# Конституция MIRA-TV

## Core Principles

### I. Единая модель сцены и единый runtime

Scene ОБЯЗАНА создаваться независимо от физического TV, содержать Slides, а каждый Slide —
Elements. Template ОБЯЗАН использовать ту же Scene Schema и тот же визуальный движок.
Preview и TV Player ОБЯЗАНЫ получать один Scene Model, один канонический источник
`catalog_items` и использовать общие Scene Renderer и `ScenePlaybackRuntime`. Создание
параллельного renderer, runtime или отдельной модели для одного экрана ЗАПРЕЩЕНО. TV Player
ОБЯЗАН читать только опубликованную неизменяемую Scene Revision и НИКОГДА не читать Draft.

Обоснование: единый контракт исключает расхождение Preview и TV и не позволяет разным частям
системы незаметно развиваться как отдельные продукты.

### II. Canvas-first UX и визуальный паритет

Canvas ОБЯЗАН оставаться центром Scene Editor. Частые действия ОБЯЗАНЫ быть доступны сразу,
редкие настройки — раскрываться постепенно, а новый Element — давать пригодный результат с
безопасными значениями по умолчанию. Выделение или изменение одного Element НЕ ДОЛЖНО
пересоздавать остальные объекты, перезапускать видео или неожиданно перестраивать интерфейс.
Preview ОБЯЗАН показывать фактический Player runtime без служебных слоёв редактора.

Функция НЕ СЧИТАЕТСЯ готовой, если она требует лишних действий, даёт заметную задержку при
drag/resize, теряет состояние либо отображается в Preview и TV по-разному.

### III. Устранение первопричины и минимальное изменение

Каждое исправление ОБЯЗАНО устранять источник дефекта на правильной границе модели, контракта
или runtime. CSS-костыли, дополнительные таймеры, повторные запросы и дублирование логики
ЗАПРЕЩЕНЫ, если они только маскируют рассинхронизацию. Изменение ОБЯЗАНО быть минимальным и
полным; несвязанные рефакторинги и новые подсистемы не входят в задачу без отдельного решения.

Существующее публичное поведение и сохранённые данные ОБЯЗАНЫ оставаться совместимыми, если
спецификация явно не утверждает их изменение и безопасный переход.

### IV. Явное владение состоянием и совместимость данных

Каждое состояние ОБЯЗАНО иметь один источник истины. Любой параметр из `.env` управляется
ТОЛЬКО `.env` и НЕ МОЖЕТ иметь конкурирующее редактируемое значение в коде, UI или БД.
Production `.env`, пароли, токены, cookie, ключи и реальные секреты ЗАПРЕЩЕНО коммитить,
выводить в логи или включать в спецификации.

PostgreSQL, Asset Storage и необходимые секреты ОБЯЗАНЫ рассматриваться как согласованное
persistent state при backup, restore, update и удалении. Scene Draft ОБЯЗАН защищаться от
потери более свежих изменений; Published Scene Revision ОБЯЗАНА быть неизменяемой. Медиа
ОБЯЗАНЫ связываться через Asset ID. Любое изменение схемы или миграция ОБЯЗАНЫ иметь проверку
совместимости, резервного копирования и восстановления.

### V. Производительность и offline-first Player

Статическая сцена ОБЯЗАНА почти бездействовать. Невидимые видео и тяжёлые анимации ОБЯЗАНЫ
приостанавливаться, неизменившиеся assets — повторно использоваться, а WebSocket — служить
сигналом для HTTPS reconciliation, а не каналом непрерывной передачи сцены. Player ОБЯЗАН
сохранять Last Known Good и восстанавливаться после offline без потери рабочей версии.

На `pointermove` ЗАПРЕЩЕНЫ сетевое сохранение, тяжёлая бизнес-логика и полная пересборка сцены.
Постоянный JavaScript render-loop допускается ТОЛЬКО при измеренной необходимости, которую
нельзя закрыть CSS/WAAPI или событием. Производительные изменения ОБЯЗАНЫ проверять, что они
не ухудшили плавность Editor, загрузку Player, сеть и CPU в состоянии покоя.

### VI. Проверка на уровне причины

Каждый исправленный отказ ОБЯЗАН получить регрессионную проверку на уровне, где находилась
причина: unit для model/geometry/pricing/timeline; integration для API/DB/assets; browser для UX;
Player parity для общего Scene Model; production image для runtime-зависимостей; multi-TV для
viewport и синхронизации. Изменение Scene Model, пользовательского workflow или границы модулей
ОБЯЗАНО обновлять документацию в том же изменении.

Минимальный обязательный набор проверок определяется затронутыми слоями, но успешный локальный
узкий тест НЕ ЗАМЕНЯЕТ полный применимый набор перед Pull Request.

### VII. Дисциплина веток и релизов

`main` ОБЯЗАН оставаться стабильной эксплуатационной линией MIRA-TV 1.0.3. Новая Scene
Architecture разрабатывается от утверждённой линии `prototype` в отдельной рабочей ветке.
Незавершённый prototype-код ЗАПРЕЩЕНО переносить в `main`. Версию 1.0.4, тег, GitHub Release,
merge в `main` и production update ЗАПРЕЩЕНО выполнять без отдельного явного решения владельца.

Стандартный путь изменения: выделенная ветка → локальные проверки → Pull Request → успешные
`node-check`, `compose-check` и `browser-visual` → review → squash merge. Push, создание или
merge Pull Request и изменение production требуют явного разрешения на соответствующее действие.

## Технические и продуктовые ограничения

- Базовый stack: Node.js 24+, ES modules, Express 5, PostgreSQL 17, Docker Compose и текущий
  reverse proxy. Новая hosted-инфраструктура требует отдельного архитектурного решения.
- Несколько TV образуют ТОЛЬКО горизонтальный ряд. Вертикальные и 2×2-группы, Master TV и
  прямая синхронизация TV друг с другом не входят в текущую архитектуру.
- Новый Widget ОБЯЗАН подключаться как Element через общий registry/contract, а не как отдельная
  подсистема. Произвольный пользовательский JavaScript или HTML ЗАПРЕЩЁН базовой моделью.
- Бизнес-логика цены ОБЯЗАНА выполняться на сервере. Preview и Published Player ОБЯЗАНЫ получать
  один и тот же канонический CatalogItem contract.
- AI НЕ ВХОДИТ в текущую архитектурную фазу до завершения эксплуатационной проверки ручного
  конструктора.
- До окончания VPS/TV-приёмки single-TV пути новые архитектурные возможности НЕ ДОБАВЛЯЮТСЯ;
  устраняются только блокирующие эксплуатационные дефекты и выполняются одобренные изменения
  процесса разработки.

## Процесс разработки и контроль качества

1. Новая ограниченная задача ОБЯЗАНА начинаться с `$speckit-specify`, фиксирующего сценарии,
   критерии приёмки, границы и явно исключённые изменения.
2. Существенные неоднозначности ОБЯЗАНЫ быть закрыты через `$speckit-clarify` до планирования.
3. `$speckit-plan` ОБЯЗАН ссылаться на фактические модули репозитория, выполнять Constitution
   Check и фиксировать совместимость данных, производительность, rollback и применимые тесты.
4. `$speckit-tasks` ОБЯЗАН формировать небольшие проверяемые задачи с точными путями. Перед
   реализацией артефакты ОБЯЗАНЫ пройти `$speckit-analyze`, если изменение пересекает несколько
   контрактов или runtime-границ.
5. `$speckit-implement` МОЖНО выполнять только после утверждения спецификации и плана владельцем.
   Реализация ОБЯЗАНА следовать задачам без незаявленного расширения scope.
6. Перед Pull Request ОБЯЗАТЕЛЬНЫ применимые команды из `CONTRIBUTING.md`: `npm ci`,
   `npm run build`, `npm test`, `npm run test:browser`, `npm run check`, `bash -n mira-tv.sh` и
   `docker compose config --quiet`. Неприменимая или недоступная проверка ОБЯЗАНА быть явно
   указана с причиной.
7. Итоговый diff ОБЯЗАН быть проверен на случайные файлы, кэш, секреты, несвязанные изменения и
   несоответствие спецификации. Документирование и Spec Kit НЕ ТРЕБУЮТ изменения версии продукта.

## Governance

Эта конституция является обязательным gate для всех будущих Spec Kit спецификаций, планов,
задач и review в MIRA-TV. При конфликте действует последнее явное решение владельца проекта;
после него конституция и зависимая документация ОБЯЗАНЫ быть приведены в соответствие.

Изменение принципов требует: описания причины, Sync Impact Report, проверки связанных документов
и шаблонов, явного утверждения владельцем и семантического изменения версии конституции. MAJOR
означает удаление или несовместимое переопределение принципа; MINOR — новый принцип или
существенное расширение управления; PATCH — уточнение без изменения смысла. Каждый план и Pull
Request ОБЯЗАН явно подтвердить соблюдение конституции либо перечислить нарушение с обоснованием
и одобренным способом устранения.

Операционные детали определяются `CONTRIBUTING.md`, `docs/ARCHITECTURE.md`,
`docs/UX-PRINCIPLES.md`, `docs/SCENE-PROTOTYPE.md` и актуальной CI-конфигурацией. При расхождении
исторического документа с кодом или более свежим утверждённым решением фактическое состояние
ОБЯЗАНО быть проверено до изменения.
