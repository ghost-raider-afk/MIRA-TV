# Разработка MIRA-TV

Этот документ фиксирует правила разработки новой архитектуры в ветке `prototype`.

## Ветки

- `main` — стабильная эксплуатационная линия;
- `prototype` — новая Scene Architecture;
- hotfix/release-ветки не смешиваются с экспериментальной переработкой конструктора.

Нельзя переносить незавершённый prototype-код в `main` только потому, что отдельный экран уже выглядит готовым.

## Главные архитектурные инварианты

Перед изменением кода проверьте, что решение не нарушает следующие правила:

- Scene создаётся независимо от физического TV;
- Scene содержит Slides, а Slide — Elements;
- несколько TV образуют только горизонтальный ряд;
- Preview и Player должны прийти к одному Scene Renderer;
- новый Widget подключается как Element, а не как отдельная параллельная подсистема;
- дизайн и эксплуатационное назначение сцен разделены;
- бизнес-логика цены остаётся на серверной стороне;
- TV Player выполняет минимум лишней работы;
- PostgreSQL, Assets и необходимые секреты рассматриваются как согласованное persistent state.

## UX — часть архитектуры

Перед добавлением возможности прочитайте [docs/UX-PRINCIPLES.md](docs/UX-PRINCIPLES.md).

Функция не считается готовой, если она требует лишних действий, заметно тормозит drag/resize, неожиданно перестраивает интерфейс или ведёт себя иначе в Preview и Player.

Не компенсируйте неудобный workflow дополнительными настройками.

## Root-cause правило

Исправление должно устранять источник дефекта. Не добавляйте CSS/таймер/повторный запрос только для маскировки расхождения двух моделей или лишнего рендера.

Если Preview и Player отличаются, ищите расхождение Renderer/Scene Model, а не создавайте отдельный набор поправок для одного из них.

## Требования для разработки

- Node.js 24+;
- npm;
- Docker + Docker Compose;
- Git;
- Playwright/Chromium для browser tests.

```bash
npm ci
npm run build
npm test
npm run test:browser
npm run check
```

Проверка production compose:

```bash
docker compose config --quiet
```

## Spec-driven разработка

В репозитории подключён GitHub Spec Kit для Codex. Каждая новая ограниченная задача проходит
последовательность `$speckit-specify` → `$speckit-plan` → `$speckit-tasks` →
`$speckit-implement`. Для неоднозначных требований используется `$speckit-clarify`, а перед
реализацией изменений нескольких контрактов — `$speckit-analyze`.

Обязательные принципы находятся в `.specify/memory/constitution.md`. Порядок запуска, структура
артефактов и правила веток описаны в [docs/SPEC-KIT.md](docs/SPEC-KIT.md).

## Prototype и данные

Пока Scene Schema репетируется, `localStorage` допускается только как явно временное хранилище UX-прототипа.

Не создавайте финальную PostgreSQL-миграцию для Scene только ради того, чтобы «сохранение уже было на сервере». Сначала должен стабилизироваться пользовательский workflow и контракт данных.

## Производительность Editor

На `pointermove` нельзя выполнять тяжёлые операции, сетевые сохранения и полную пересборку сцены без необходимости.

Изменение одного элемента должно обновлять минимально необходимую часть состояния.

## Производительность Player

Статическая сцена должна почти бездействовать. Невидимые видео и анимации приостанавливаются. Неизменившиеся Asset повторно используются. WebSocket является сигналом изменения, а не каналом непрерывной передачи сцены.

Подробнее: [docs/PERFORMANCE.md](docs/PERFORMANCE.md).

## Новые Element

Перед добавлением нового типа Element необходимо определить:

- schema данных;
- renderer;
- inspector UI;
- defaults;
- допустимые эффекты/анимации;
- asset/data dependencies;
- поведение при отсутствии данных;
- browser tests.

Не добавляйте `if/else`-цепочку по всему приложению для каждого нового Widget. Целевая модель предполагает registry/contract.

## Тесты

Изменение должно иметь тест на тот уровень, где реально находилась причина:

- unit — geometry, pricing, model, timeline;
- integration — DB/API/asset lifecycle;
- browser — UX и редактор;
- Player parity — одинаковый Scene Model в Preview и Player;
- production image — внешние runtime-зависимости внутри собранного Docker image;
- multi-TV — viewport и синхронизация нескольких Player.

## Документация

Если меняется Scene Model, пользовательский workflow или граница модулей, документация обновляется в том же изменении.

Исторический `CHANGELOG.md` не переписывается под новую архитектуру задним числом.

## Секреты

Никогда не коммитьте `.env`, пароли, cookie, токены, приватные ключи и реальные секреты базы или сессий.
