# Разработка MIRA-TV

Проект ориентирован на надёжную работу подключённых телевизоров, включая слабые Android TV и старые Chromium. Приоритет: **надёжность → архитектура → производительность → UX → скорость разработки**.

## Технологии и запуск тестов

Требуются Node.js 24+, npm, Git, Docker/Compose и Playwright для браузерных тестов. Backend — Express 5 и PostgreSQL 17; фронтенд и Player написаны на нативном JS/HTML/CSS/SVG.

~~~bash
npm ci
npm run build
npm test
npm run test:browser
npm run check
docker compose config --quiet
~~~

`npm run check` запускает syntax/build и Node unit tests; DB, Docker, browser/visual и Android TV проверки должны выполняться дополнительно в соответствующих окружениях CI. Не выдавайте локальный `npm run check` за полный Final CI.

## Порядок изменений

1. Проверить `main`, открытые PR, HEAD SHA, релиз и результаты CI.
2. Изучить компонент-владелец проблемы и последние изменения, определить root cause.
3. Исправить общий механизм минимальным совместимым diff; не создавать параллельный renderer, новую инфраструктуру или зависимость без необходимости.
4. Сохранить API, данные PostgreSQL, исторические миграции, Docker volumes, установщик, регистрацию TV, Local-first LKG и старые сцены.
5. Для UI проверить Scene Editor → Preview → TV на общем `PlayerSceneRenderer`, responsive и слабый Android TV.
6. Добавить релевантный regression-тест, проверить performance, код, случайные файлы и секреты.

В production используется **статический live-render**. Меню рисуется через общие render model/layout и SVG; не добавляйте Video Mode, Render Agent, runtime плейлистов сцен и motion engine. В неизменном состоянии экран должен почти бездействовать.

## CI, merge и release

Во время разработки запускайте только быстрые и релевантные проверки. Полный **Final CI** выполняется один раз на окончательном PR HEAD: unit, DB, Docker/Compose, browser/e2e, visual, Android-TV и performance regression. Любое изменение после проверки требует новой финальной проверки.

Merge допустим только после успешного Final CI. После squash merge сопоставьте Git tree проверенного PR и `main`; если дерево одинаково, не запускайте полный CI повторно. После merge выполните production smoke: согласованность версии, Compose, старт, `/readyz`, Preview/Player.

**Релиз — отдельная операция после успешных проверок.** Завершённым он считается только после появления опубликованного GitHub Release и успешного release workflow. Изменение документации и открытие PR не считаются релизом.

## Безопасность

Нельзя коммитить `.env`, пароли, cookies, сессионные токены, приватные SSH-ключи или производственные данные. Для примеров используйте `.env.example`. Не отключайте и не ослабляйте тесты ради зелёного CI.

## Документация

Рабочие файлы `README.md`, `CONTRIBUTING.md` и `docs/*.md` должны соответствовать текущему `main`. Планы отмечаются как планы, открытые PR — как неслитые, а `CHANGELOG.md`/`docs/releases/` сохраняются как история. Не ссылайтесь на отсутствующие документы и не объявляйте ранее удалённые возможности действующими.
