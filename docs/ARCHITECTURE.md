# Целевая архитектура MIRA-TV

## Назначение

MIRA-TV — система создания визуальных сцен и централизованного управления их показом на одном или нескольких телевизорах.

Новая архитектура отделяет создание дизайна от физической эксплуатации TV.

```text
Каталог и медиа
       ↓
Конструктор сцен
       ↓
Шаблон сцены
       ↓
Торговая точка
       ↓
TV / группа TV
       ↓
Режим показа
       ↓
TV Player
```

## Основные домены

### Scene Authoring

Отвечает за создание сцены, слайдов, элементов, эффектов, анимации и Preview. Не знает о конкретном устройстве в торговой точке.

### Catalog

Хранит универсальные позиции, категории, свойства, базовые цены, объёмы и ручные ценовые варианты. Table Element получает данные из каталога через data binding.

### Media

Хранит изображения, логотипы и видео как управляемые Asset. Сцена ссылается на Asset ID, а не на случайные файловые пути.

### Operations

Хранит торговые точки, TV, экранные группы, назначения шаблонов, плейлисты и расписания.

### Player Runtime

Получает подготовленное состояние сцены, отображает только свой viewport, кеширует необходимые ресурсы и сохраняет последнюю рабочую версию.

## Главные сущности

```text
Scene
Slide
Element
Template
MediaAsset
CatalogCategory
CatalogItem
CatalogPriceVariant
Location
DisplayGroup
DisplaySlot
Device
Assignment
Playlist
Schedule
```

`Template` — сохранённая для повторного использования сцена. Он не должен иметь отдельного визуального движка: шаблон использует ту же Scene Schema.

## Scene Model

```text
Scene
 ├─ canvas
 ├─ display_count
 └─ slides[]
      ├─ background
      ├─ duration
      ├─ transition
      └─ elements[]
```

Element имеет общий контракт геометрии, слоя, видимости, стиля, data binding, эффектов и анимации.

## Один Renderer

Preview и TV Player обязаны использовать один Scene Renderer или одну общую библиотеку рендеринга.

```text
Scene Model
    ↓
Scene Renderer
   ↙       ↘
Editor    Player
```

Editor добавляет только служебные слои: выделение, направляющие, resize handles, drag и Inspector.

## Authoring и Runtime

Редактору нужна полная модель сцены. Телевизору — минимально достаточная runtime-модель.

```text
Authoring Scene
      ↓
Scene Compiler
      ↓
Runtime Snapshot
      ↓
TV Player
```

Scene Compiler в будущем разрешает ссылки на каталог, цены, погоду, медиа и настройки конкретной торговой точки до передачи данных Player.

## Широкоформатный ряд TV

Поддерживается только горизонтальное объединение:

```text
TV 1 | TV 2 | TV 3 | ... | TV N
```

Сцена имеет один глобальный Canvas. Для Full HD ширина равна `1920 × количество TV`, высота — `1080`.

Каждый Player получает собственный viewport. Объект может пересекать границу двух TV, но важные данные должны по возможности располагаться с учётом физических рамок.

Сетки 2×2 и вертикальные группы не входят в целевую архитектуру текущей линии.

## Синхронизация нескольких TV

TV не должны синхронизироваться друг с другом и не должны иметь Master TV.

Целевая модель использует общую временную шкалу от сервера. Каждый Player вычисляет текущий слайд и позицию анимации относительно согласованного времени.

## Хранение

Целевая серверная реализация использует PostgreSQL для бизнес-данных и отдельное постоянное Asset Storage для файлов.

База и Asset Storage рассматриваются как единое persistent state для backup, restore, update и удаления.

Текущий `localStorage` в `prototype` — только временный способ репетировать UX.

## Обновления Player

WebSocket используется как лёгкий сигнал «состояние изменилось». Сами сцены и медиа передаются по HTTPS.

Player сравнивает версии и хэши, не получает всё заново без причины и заменяет Last Known Good только после успешной подготовки новой рабочей версии.

## Расширяемость

Новые информеры не должны создавать отдельные подсистемы. Они подключаются как Element через единый registry/contract.

Примеры будущих элементов: курс валют, RSS, новости, очередь, расписание, внешние данные.

Произвольный пользовательский JavaScript или HTML не входит в базовую модель из-за безопасности и сложности runtime.
