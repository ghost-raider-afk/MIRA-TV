# MIRA-TV — интерфейс Telegram / MAX

**Этап:** базовые компоненты интерфейса и проверка подписанных данных. Это не запущенный бот: отсутствуют рабочий транспорт бота, подтверждение отправителей через webhook, доставка событий, Mini App страницы и production credentials. Развёртывание не разрешено до интеграционных и security-тестов.

## Платформы и UI

| Поведение | Telegram | MAX |
| --- | --- | --- |
| Компактное уведомление | HTML Widget Bot API 10.4 в личном чате; простой текст + кнопка в остальных случаях | Сообщение + кнопка |
| Рабочее место | Main Mini App | Mini App + MAX Bridge |
| Обновление карточки «ТВ офлайн» после восстановления | \`editMessageWidgetData\` для того же сообщения без нового уведомления; отдельное уведомление восстановления по утверждённой настройке | Отправка/редактирование платформенного сообщения, если поддерживается |
| Тёмная/светлая тема | Telegram theme variables и тема Mini App | MAX Bridge и CSS tokens |
| Доступ к CRM | Только после серверного подтверждения аккаунта и роли | То же |

Telegram Widgets появились 09.11.2026. На production они разрешены только в **личных чатах с ботом**; в чате неподдерживаемого клиента интерфейс может выглядеть как неподдерживаемое медиа. Для всех критических тревог обязательна текстовая подпись; возможность выключить виджеты предусмотрена. HTML Widget — не Mini App: это фиксированный HTML без сетевых запросов и полей ввода. Данные меняет только бот через \`chat_data\`, максимум 1024 UTF-8 байт. Размер HTML не более 32768 байт исходно и 4096 байт после zlib deflate 9.

## Дизайн

**Карточка Telegram:** метка «Офлайн / Онлайн / CRM», точка, ТВ или тема заявки, время, кнопка «Подробнее» для раскрытия небольшого текстового блока; под карточкой — кнопка «Открыть MIRA-TV» в Mini App. Ключевые данные остаются в подписи сообщения, доступной даже без поддержки виджетов. Данные в DOM присваиваются только через \`textContent\`, исходный HTML не содержит имени точки или пользовательских строк.

**Mini App администратора:** вкладки «Мониторинг», «Заявки», «Уведомления». В мониторинге: статус точек и ТВ, карточки инцидентов, переход к истории диагностики; в заявках — разрешённые действия CRM и аудит. Никаких функций, не поддержанных основным API.

**Mini App менеджера:** вкладки «Мои точки», «Заявки», «Уведомления». Создание заявки через существующий CRM workflow, статусы, комментарии, исправления. Доступ только к назначенным точкам. Компактный mobile-first интерфейс на нативных HTML/CSS/JS, без React и параллельной CRM.

**Адаптеры:** Telegram \`Telegram.WebApp.initData\` и MAX \`window.WebApp.initData\` передаются backend для проверки подписи. Клиентские \`initDataUnsafe\` и \`start_param\` не определяют права доступа. Функция \`verifyMiniAppInitData\` подтверждает *только идентичность в мессенджере*; далее необходима привязка к учётной записи MIRA-TV и проверка актуальной роли/точек сервером. Срок действия подписи для сессии — не более 10 минут, с отклонением времени до 60 секунд. Токены Telegram и MAX различны.

## Безопасность и жизненный цикл

1. Администратор назначает Telegram/MAX User ID в настройках пользователя. Бот принимает действия только с достоверным sender ID из проверенного webhook и каждый раз сверяет его с актуальной ролью и активностью пользователя. Самостоятельная привязка отложена.
2. Все операции с заявками, статусами и точками исполняет существующий сервер MIRA-TV с повторной проверкой прав. Нельзя доверять параметрам Mini App, widget request, chat ID или подписанному messenger ID как роли.
3. Состояние offline определяется серверным WebSocket-событием, **подтверждается через 120 секунд**, затем проходит через durable outbox PostgreSQL; восстановление сообщает отдельно, дубли того же инцидента подавляются.
4. После рестарта сервера/бота не создавать ложные offline. Доставку отмечать только после подтверждения платформой; не считать исключение/timeout успехом. Не отправлять токены, адреса устройств и секреты в чат.
5. Сервис бота — отдельный Docker, без публикации внутреннего порта и без прямого подключения к БД; он обращается к основному приложению по аутентифицированному внутреннему API. LKG и TV Player не изменяются.

## Текущее реализованное основание

- \`src/bot/telegram-widgets.js\` — шаблон Telegram HTML Widget, сериализация безопасного \`chat_data\`, метод отправки \`sendWidget\` и контролируемый fallback \`sendMessage\` через внедрённый транспорт.
- \`src/bot/miniapp-auth.js\` — HMAC-проверка Telegram/MAX initData (без выдачи прав MIRA-TV).
- Regression tests проверяют лимиты, недопустимые данные, подписи, устаревшие launch-параметры и fallback.

## Внешние требования

- Telegram: https://core.telegram.org/bots/widgets , https://core.telegram.org/bots/webapps
- MAX: https://dev.max.ru/docs/webapps/introduction , https://dev.max.ru/docs/webapps/bridge , https://dev.max.ru/docs/webapps/validation
- **MAX для партнёров требует подтверждённый профиль юрлица, ИП или самозанятого — резидента РФ.** До получения доступа невозможно проверить реальный бот и Mini App MAX, поэтому его нельзя объявлять готовым.
- Ключи и токены создаются пользователем в платформенных кабинетах, вне репозитория. Ни один из адаптеров не должен делать TV зависимым от стороннего мессенджера.

## MAX transport adapter — 12.11.2026

Добавлен `src/bot/max-notices.js` на основе официального `POST /messages`: адрес `platform-api2.max.ru`, токен только в заголовке `Authorization`, ограничение 2 сообщения/сек на диалог. Кнопка `open_app` использует имя зарегистрированного MAX-бота; обычные HTTPS-адреса открывает кнопка `link`. Общий файл `src/bot/notice-content.js` задаёт одинаковые тексты и длины уведомлений для MAX и Telegram. `sendMaxNotice` принимает внедрённый транспорт, не создаёт запросы и не доставляет сообщения самостоятельно до подключения бота. Любая ошибка должна возвращаться durable outbox для повторной отправки. Пока MAX credentials и разрешения Mini App отсутствуют, онлайн-отправка не подтверждена.

**Уточнение по MAX `open_app`:** `web_app` содержит публичное имя зарегистрированного MAX-бота (`miniAppBot`), а не произвольный URL хостинга. Пока зарегистрированное Mini App не настроено, при `miniAppUrl` формируется обычная безопасная кнопка `link`. В MAX Mini App запускается только через платформу и привязанный бот; нельзя выдавать HTTPS-ссылку за подтверждённый запуск внутри MAX.

## Самостоятельная привязка — отложена

Ранее подготовленная серверная функция одноразового кода и таблица `messenger_link_codes` остаются недоступной будущей заготовкой: публичный роутер не монтируется. Текущая привязка производится только администратором через существующую таблицу `messenger_accounts`, без отдельной базы пользователей.

## Утверждённая схема привязки пользователей (13.11.2026)

**Только администратор:** «Настройки → Пользователи → Telegram и MAX» — числовые идентификаторы Telegram User ID и MAX User ID для администраторов и менеджеров. Пустой ID = нет доступа к соответствующему боту. Привязки хранятся в единой `messenger_accounts` с уникальностью `(provider,provider_user_id)`. Активность и роль пользователя проверяются по `web_users` при каждом действии, а ограничения по торговым точкам — через действующие CRM API. Webhook sender ID должен быть подтверждён самой платформой; подставить чужой ID в HTTP-запрос недостаточно.

**Самостоятельная привязка через личный кабинет отложена.** В текущей версии `/api/messenger-links` не монтируется и не выдаёт кодов. Серверная подготовка одноразовых кодов остаётся недоступной будущей заготовкой. Доступен только административный API `GET /api/admin/managers/messenger-users` и `PUT /api/admin/managers/messenger-users/:username`. Его защищает существующий middleware роли администратора; в журнале сохраняется изменение без раскрытия ID. Значения `TELEGRAM_ADMIN_ID` и `MAX_ADMIN_ID` в .env.bot не дают обхода: их также нужно назначить соответствующему пользователю MIRA-TV.
