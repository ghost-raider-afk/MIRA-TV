# Перенос сервера MIRA-TV по SSH

## Состояние реализации

Реализованы SSH-сопряжение, диагностика и передача предварительного архива с PostgreSQL, ресурсами, секретами и HTTPS-хранилищем. Архив проверяется по списку допустимых файлов и SHA-256. Новый сервер автоматически восстанавливает предварительную копию во внутренних контейнерах, проверяет PostgreSQL, регистрации ТВ и /readyz, затем останавливает тестовое приложение, не запуская публичный Traefik. При этом источник продолжает работать, поэтому архив **не является финальным согласованным снимком**. В коде добавлены блокировка записи на исходном сервере (включая политику Docker restart), финальный архив и полная замена предварительной БД/ресурсов на новом сервере; при сбое до переключения предусмотрено восстановление источника. В черновой ветке также реализованы HTTPS/WebSocket-переключение, попытка автоматического отзыва SSH-ключа и таймер контроля старого прокси. **Эти операции ещё не проверены на двух независимых серверах и не опубликованы в релизе.** DNS меняется администратором вручную. До интеграционных проверок не используйте механизм для production.

## Утверждённый сценарий

1. На существующем сервере запустить MIRA-TV → «Миграция на другой сервер» → «Этот сервер — исходный».
2. Указать публичный IPv4 и SSH-порт. Установщик выдаёт одноразовый секретный комплект MIRA1, содержащий временный приватный ключ и pinned SSH host key.
3. На новом пустом сервере запустить установщик → «Миграция на другой сервер» → «Этот сервер — новый», вставить комплект.
   После проверки предварительной копии будет запрошен публичный IPv4 нового сервера. Дальнейшая финальная синхронизация и переключение выполняются одним сценарием; IPv4 и доступность 443 обязательны.
4. Новый сервер устанавливает соединение по SSH с обязательной проверкой host key, подтверждает версию, HEAD и домен исходного сервера, затем скачивает предварительный архив и проверяет SHA-256.
5. Новый сервер разворачивает внутреннюю предварительную копию и проверяет готовность приложения. При сбое подготовки контейнеры и созданные Docker volumes удаляются с нового сервера; архив остаётся для повторной подготовки через меню. Если сервер выключился во время восстановления, можно безопасно удалить только помеченную как тестовую установку через «Отменить подготовку нового сервера», затем повторить подготовку.
6. В коде добавлены включение нового Traefik и перенаправление HTTPS/WebSocket через старый сервер с проверкой сертификата и SNI исходного домена. При начале активации старый сервер необратимо блокируется для записи; ошибку после этого этапа разрешается исправлять только без включения старой БД.
7. **Осталось:** проверка перехода DNS, проверка механизма автоматического отключения старого прокси, полноценные интеграционные испытания на двух серверах и подтверждение отсутствия потери данных.

Предварительная копия на новом сервере остаётся в закрытом каталоге /var/lib/mira-tv/migration/staged и содержит секреты .env и сертификата. Для отказа от миграции удалите её через пункт «Удалить предварительную копию» на новом сервере.

Приватный SSH-ключ показывается один раз. Не пересылайте его в чаты и не публикуйте. Начните перенос в течение 24 часов после выдачи ключа. При успешной проверке SSH и каждые 5 минут во время активного создания предварительного архива источник автоматически продлевает 24-часовой период доступа. Общий абсолютный срок действия ключа — 7 дней: после него потребуется новая выдача. Если передача прервётся и SSH не будет использоваться более 24 часов, для возобновления также потребуется новый ключ. При подтверждённом переключении установщик пытается автоматически отозвать SSH-ключ; если отзыв не подтвердился, требуется ручной отзыв на исходном сервере. Переходный HTTPS-прокси не должен зависеть от SSH-ключа.

На сервере должен быть разрешён вход по SSH-ключу для root (без включения парольной аутентификации); если политика безопасности сервера запрещает root SSH, сопряжение завершится ошибкой. В будущем перенос можно адаптировать под отдельного ограниченного пользователя.

## Инварианты полной миграции

- Сохраняется тот же домен и SESSION_SECRET, существующие tv_devices, tv_device_bindings, tv_device_sessions и все веб-сессии.
- База PostgreSQL и site-assets передаются в согласованном состоянии, а не простым копированием открытого каталога PGDATA.
- Целевой сервер не должен перезаписывать чужие Docker volumes и существующую установку.
- До успешной проверки /readyz, авторизации ТВ и состава ресурсов старый сервер остаётся основным.
- После переключения базы нельзя независимо принимать записи на обоих серверах.
- Отсутствие DNS-записи старого IP не доказывает, что на него не обратится давно выключенный Android TV. Завершение прокси требует консервативной политики и контроля старых подключений.
- Обновление релиза и миграция сервера остаются отдельными операциями.

## Вывод старого прокси

После подтверждённого переключения исходный сервер устанавливает таймер systemd, который раз в час проверяет DNS и доступность HTTPS нового сервера. Прокси автоматически останавливается только если все полученные A-записи указывают на новый IPv4, AAAA-записей нет, нет активных TCP-соединений со старым HTTPS, и счётчики сетевого трафика контейнера прокси не изменялись 14 дней. При сбросе счётчиков, перезапуске контейнера или неудачной проверке вывод из эксплуатации не выполняется. Данные исходной базы и её блокировка записи сохраняются.

**Ограничение:** невозможно доказать по DNS, что выключенный месяцами телевизор не сохранил старый IP. Для абсолютной гарантии доступа всех когда-либо зарегистрированных ТВ старый IP должен оставаться доступным, пока не подтверждён фактический переход каждого устройства. Автоматическое отключение по 14-дневному отсутствию трафика — консервативная эвристика, а не математическая гарантия для длительно отключённых ТВ. До реальных испытаний автоматику применять в production нельзя.
