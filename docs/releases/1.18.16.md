# MIRA-TV 1.18.16

Table rendering and manager workflow release.

## Table renderer

- Restores shared table content scaling for Classic and `Читаемый · 2 колонки` layouts.
- Rows without secondary product metadata use a compact shared geometry instead of reserving an empty second line.
- Section rows now carry an explicit `Продукция` / `Тара` type; packaging sections suppress litre column headings without relying on section names.
- Litre column headings keep the section title color and gain thin vertical separators inside the section bar: `Название | 1 Л | 1,5 Л` in Classic and `Название | 1 Л` in the two-column layout.
- Classic and two-column layouts use the same lighter table surface opacity.
- Editor, Preview and TV continue to use the same render model, layout and SVG renderer.

## Manager workspace

- Existing `/manager` TV cards and fullscreen view now render current server state with the canonical `PlayerSceneRenderer`; ordinary manager previews no longer request physical TV screenshots.
- Physical TV screenshots remain available only through the existing administrator diagnostic path.
- Manager catalog is read-only for production data and can create product or packaging change proposals.
- Managers can see their proposal status: pending, approved, rejected or conflict, including administrator comments.
- Administrators review proposals in Catalog with an explicit old → proposed diff, optional comment, approve and reject actions.
- Approved proposals reuse the existing catalog update and Player invalidation path.
- Stale proposals are rejected as conflicts when the source catalog record changed after the proposal was created.
- No manager CSV or bulk-import path was added.

## Compatibility

- Existing sections default to `Продукция`, so historical menus remain valid until an administrator explicitly marks a section as `Тара`.
- Migration `036-catalog-change-proposals` only adds proposal storage; existing catalog, menu and scene data are preserved.
- PostgreSQL data volumes, public Player APIs, Docker volumes and Local-first Player lifecycle remain compatible.
