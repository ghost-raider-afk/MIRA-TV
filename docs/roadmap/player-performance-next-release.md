# План оптимизации TV Player для следующего релиза

## Цель

Снизить постоянную нагрузку на CPU и RAM телевизора без ухудшения актуальности контента и без упрощения визуальных возможностей.

## Базовый принцип архитектуры

Перейти от модели «каждый объект сам запускает свою анимацию» к централизованной модели:

`delta -> compile changed scene -> preload -> atomic swap -> one animation runtime -> sleep when static`

Ключевые компоненты:

- один контур управления `Admin -> Scene State -> Player Context -> TV`; Preview не имеет собственного альтернативного renderer/state source;
- Preview выбранного телевизора стартует из его `screen_animation_settings`, а не из общего шаблона;
- каждый объект сцены имеет независимые состояния `visible` и `animation_enabled`;
- weather входит в тот же component/delta pipeline и тот же порядок слоёв, что остальные объекты;
- Apply публикует одну атомарную scene revision без промежуточных сохранений отдельных подсистем.


- `Scene Compiler` — собирает единый план отображения и анимации для текущего экрана.
- `Animation Runtime` — один централизованный scheduler/timeline для всех активных визуальных эффектов.
- Component-level recompilation — при изменении пересобираются только затронутые компоненты, а не вся сцена.

## 1. Группировка анимаций

Все одинаковые или синхронные анимации должны объединяться в одну логическую группу до показа на телевизоре.

Пример: если несколько акционных строк используют одинаковые `badge`/`glow` эффекты, не создавать отдельный независимый animation instance на каждую строку. Вместо этого формировать одну общую animation track/group и применять её ко всей группе целей.

Цель: уменьшить количество одновременно живущих animation objects, таймеров, compositor layers и служебных объектов браузера.

## 2. Единый Scene Animation Plan

Scene Compiler должен собирать компактный план текущей сцены, например:

```js
scene = {
  duration: 8000,
  tracks: [
    { target: 'promotion-group', ... },
    { target: 'entity', ... },
    { target: 'background-fx', ... }
  ]
}
```

Плеер не должен позволять отдельным компонентам независимо запускать собственные бесконечные циклы, если их можно объединить в общий runtime.

## 3. Пересборка только изменившихся компонентов

Использовать существующую delta/hash архитектуру как основу.

План сцены должен быть разбит на независимые логические блоки:

- menu
- promotion
- entity
- weather
- background
- playlist
- animation/runtime

Если изменился только `menu`, пересобираются только `menu` и связанные с ним `promotion` tracks. Неизменившиеся блоки переиспользуются из текущего плана.

Не выполнять полную пересборку сцены без необходимости.

## 4. Атомарное переключение сцены

При получении `context.changed`:

1. Получить delta.
2. Построить новый/частично обновлённый Scene Plan в памяти.
3. Подготовить критические изображения, SVG, видео и другие ресурсы.
4. Не изменять текущую активную сцену, пока новая версия не готова полностью.
5. Выполнить одно атомарное переключение старого состояния на новое.
6. Немедленно уничтожить устаревшие animation/media runtime объекты старой сцены.

Это должно исключить промежуточные DOM-состояния, повторные layout/reflow и кратковременное дублирование большого количества активных анимаций.

## 5. Sleep when static

Animation Runtime должен полностью переходить в состояние покоя, если одновременно выполняются условия:

- нет активного видео;
- нет активных анимаций;
- нет перехода сцены;
- нет изменения контекста.

В статическом состоянии не должно быть постоянного `requestAnimationFrame`, периодического layout или другого рендер-цикла.

## 6. Медиа и память

Для сменённого/невидимого видео и других тяжёлых ресурсов требуется строгий lifecycle:

- `pause()`;
- освобождение source/resource;
- удаление ненужного DOM-узла;
- `load()` при необходимости сброса media pipeline;
- `URL.revokeObjectURL()` для временных Blob URL;
- не держать декодированными все элементы плейлиста одновременно.

Рекомендуемая модель: активная сцена + максимум одна заранее подготовленная следующая сцена.

## 7. Сеть и fallback

Текущий WebSocket должен остаться основным механизмом доставки изменений.

Не увеличивать heartbeat только ради экономии ресурсов: его вклад в CPU/RAM минимален.

Fallback polling использовать только при недоступном WebSocket. Рассмотреть адаптивный интервал:

`60 -> 120 -> 300 секунд`

при последовательных неизменённых ответах, со сбросом к короткому интервалу после восстановления соединения или изменения состояния.

## 8. Конфигурация

Пороговые значения и профиль производительности не должны быть разбросаны по коду.

Рассмотреть параметры `.env`, например:

- `PLAYER_RENDER_PROFILE=balanced`
- интервалы fallback polling;
- лимит одновременно активных тяжёлых эффектов;
- preload depth для плейлиста;
- лимиты локального media/runtime cache.

`.env` остаётся единым источником конфигурации.

## 9. Что не делать

- Не переводить весь UI в Canvas/WebGL только ради оптимизации.
- Не ухудшать качество текста и SVG.
- Не отключать функции ради прохождения performance-тестов.
- Не увеличивать все сетевые интервалы без разбора реального механизма.
- Не оставлять параллельно старый и новый animation runtime после переключения сцены.

## Ожидаемый итог

После внедрения архитектура TV Player должна работать по принципу:

`delta -> compile changed scene -> preload -> atomic swap -> one animation runtime -> sleep when static`

Главная цель нового релиза: уменьшить количество независимых постоянно работающих animation instances и сократить время жизни ненужных media/runtime объектов, сохранив текущие визуальные возможности и быстрые обновления через WebSocket.
